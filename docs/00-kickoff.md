## 1. 팀 구성 및 역할

한 명의 에이전트가 수행하지만, 아래 6개 역할로 나누어 각 역할의 관점에서 검토·질문·산출물을 관리한다.

| 역할 | 담당 범위 | 주요 산출물 |
|---|---|---|
| **PM / 기획** | 요구사항 정리, 범위 통제, 타임라인, 클라이언트 커뮤니케이션 | 이 문서, 주간 체크리스트, 결정 로그 |
| **콘텐츠 / 카피** | 전시 안내 톤의 문구, 특이사항의 간접 표현, 섹션 구성 순서 | 카피 덱 (섹션별 문구 2안), OG 문구 |
| **디자인 시스템 / UI** | 레퍼런스 사이트 분석 → 토큰(색·타입·간격·모션), 컴포넌트, 인터랙션 원칙 | `tokens`, 섹션 레이아웃 스펙, 모션 가이드 |
| **프론트엔드** | 구현, 스크롤·전환 인터랙션, 모바일 성능, 접근성 | 사이트 코드, 성능 예산 리포트 |
| **폼 / 데이터** | 참석 여부·시간대·배송지·모바일 티켓 파이프라인, 개인정보 처리 | 폼 스키마, 저장소 연동, 관리자 조회 방식 |
| **QA / 릴리즈** | 실기기 테스트(iOS Safari, 카카오톡 인앱), 배포, 공유 URL, 미리보기 카드 | 테스트 체크리스트, 배포 URL |

역할 간 의존:
- 디자인 시스템은 **레퍼런스 사이트 수령**에 의존한다. 미수령 시 임시 시스템으로 착수하고 나중에 토큰만 교체한다 (교체 비용 약 1일).
- 폼/데이터는 **저장소 선택**과 **모바일 티켓의 정의**에 의존한다. 이 둘이 미결이면 폼 UI만 만들고 전송은 목업으로 둔다.

## 2. 클라이언트 확인 사항 (역할별 취합)

우선순위 표기: **[A] 초안 착수 전 필요 (9/29 월 저녁까지)**, **[B] 초안 공유 전 필요 (10/3까지)**, **[C] 최종 전 필요 (10/9까지)**

### 2.1 PM / 기획

1. **[A] 전시의 실제 운영 방식.** 12:30–19:00 동안 하객이 원하는 시간에 자유롭게 방문하는 형태인지, 아니면 특정 시각에 식(세리머니)이 있는지. 두 경우 "참석 희망 시간대" UI가 완전히 달라진다 (자유 방문 → 시간 슬롯 선택, 세리머니 있음 → 세리머니 참석 여부 + 방문 시간).
2. **[A] 시간대 슬롯 단위와 정원.** 1시간 단위인지, 30분 단위인지. 슬롯별 인원 제한이 있는지(있다면 마감 처리 필요).
3. **[A] "10월 둘째 주 공유"의 의미.** 하객 전체 발송인지, 가족·지인 소규모 리뷰인지. 또한 둘째 주를 10/5–10/11로 볼지 10/12–10/18로 볼지. 아래 타임라인은 **10/9 (금) 공유 가능**을 기준으로 잡았고, 10/12 주는 버퍼로 두었다.
4. **[B] 예상 하객 수.** 무료 티어 한도(저장소, 지도 API 호출)와 실물 티켓 수량 산정 기준.
5. **[B] 실물 청첩장·티켓 신청 마감일.** 배송 기간을 고려하면 11월 초~중순 마감이 현실적이다. 마감일이 있어야 폼에 "마감 안내"와 마감 후 처리(모바일 티켓으로 전환)를 넣을 수 있다.
6. **[B] 도메인·호스팅.** 보유 도메인이 있는지. 없으면 Vercel 기본 도메인으로 진행하고 나중에 연결.
7. **[C] 언어.** 한국어 단일인지, 영어 병기가 필요한 하객이 있는지.

### 2.2 콘텐츠 / 카피

1. **[A] 전시의 컨셉.** 전시명이 있는지, 무엇을 전시하는지(사진, 두 사람의 작업물, 공간 자체 등), 두 사람의 직업·배경이 전시와 연결되는지. **"AI로 만든 느낌"을 없애는 가장 큰 요소는 디자인이 아니라 두 사람만의 구체적인 내용이다.** 이게 없으면 어떤 디자인이든 템플릿처럼 보인다.
2. **[A] 사용 가능한 실제 자료.** 두 사람 사진, 전시장 공간 사진, 작품 이미지, 로고·타이포. 초안에는 플레이스홀더를 쓰더라도 최종 톤 판단을 위해 1–2장은 일찍 필요하다.
3. **[A] 케이터링의 실제 구성.** "식사가 제공되지 않는다"를 간접적으로 쓰려면 실제로 무엇이 있는지 알아야 한다 (예: 음료와 핑거푸드, 커피 바, 디저트). 없다면 "가벼운 다과"처럼 쓸 수 있는 범위를 확인.
4. **[B] 축의금 미수령의 대안 표현.** 방명록, 편지, 특정 문구 등 하객이 대신 할 수 있는 행동이 있는지. "받지 않습니다"만 있으면 하객이 당황한다.
5. **[B] 혼주(부모님) 표기 여부.** 청첩장 관례상 넣는 항목이지만, 전시 초청 톤(7)에서는 생략하거나 최소화하는 편이 어울린다. 넣는다면 위치와 문구 확인.
6. **[B] 드레스코드·관람 에티켓.** 있다면 안내 섹션에 포함.
7. **[C] 연락처 노출 여부.** 신랑·신부 전화번호를 사이트에 넣을지, 넣는다면 어느 위치에.
8. **[C] 인사말 초안.** 직접 쓴 문구가 있는지. 없으면 카피 2안을 제시하고 고르는 방식으로 진행.

### 2.3 디자인 시스템 / UI

1. **[A] 레퍼런스 사이트 전달 시점.** 초안을 주말까지 내려면 **9/29 (월) 저녁**까지 필요하다. 늦어지면 임시 시스템(화이트 큐브 갤러리 톤: 오프화이트 배경, 세리프 헤드라인 + 산세리프 본문, 절제된 페이드·패럴랙스)으로 착수하고 토큰만 교체한다. 레퍼런스에서 어떤 점을 참고할지도 함께 (색, 타이포, 모션, 레이아웃 중 무엇).
2. **[B] 실물 청첩장·티켓의 디자인 존재 여부.** 이미 디자인되어 있다면 사이트가 그것을 따라야 한다. 파일이나 시안 공유 필요.
3. **[B] 다크 모드.** 지원할지. 갤러리 톤이면 라이트 단일이 관리하기 쉽다. 권장: 라이트 단일.
4. **[C] 웹폰트.** Pretendard(무료) 기본 사용을 가정. 특정 세리프 폰트(예: 유료 폰트)를 원하면 라이선스 확인 필요.

### 2.4 프론트엔드

1. **[A] 지도 방식.** 네이버·카카오 지도 SDK는 API 키 발급과 도메인 등록이 필요하고, 모바일 초기 로딩을 늘린다. **권장: 정적 지도 이미지 + 네이버지도·카카오맵·티맵 딥링크 버튼.** 실제 상호작용형 지도가 꼭 필요한지 확인.
2. **[B] 인터랙션 범위 합의.** 스크롤 연동 페이드·슬라이드, 섹션 전환, "전시 구성 애니메이션"(공간 도면이 순서대로 그려지는 방식 등)까지는 포함. 3D·WebGL·대용량 영상은 모바일 사양 기준으로 배제 권장.
3. **[B] 주 접속 경로.** 카카오톡 공유가 주 경로라면 카카오톡 인앱 브라우저와 iOS Safari를 1순위 테스트 대상으로 잡는다. 문자·인스타그램 등 다른 경로가 있으면 추가.
4. **[C] 500px 초과 화면 처리.** 데스크톱에서 열었을 때 가운데 정렬 + 배경색(또는 이미지)로 둘지, 별도 데스크톱 레이아웃이 필요한지. 권장: 가운데 정렬.

### 2.5 폼 / 데이터

1. **[A] 응답 데이터를 어디서 볼 것인지.** 이 답이 저장소를 결정한다.
   - Google Sheets (Apps Script 연동): 두 사람이 시트에서 바로 보고 정렬·필터 가능, 무료. 전송 지연 1–2초.
   - Supabase: 더 안정적이고 빠르지만 관리 화면이 개발자 지향.
   - 권장: **Google Sheets**. 배송 라벨 출력·티켓 수량 집계가 시트에서 바로 된다.
2. **[A] 모바일 티켓의 정의.** 첨부 흐름도의 "번호 입력(모바일 티켓)"이 무엇을 뜻하는지가 가장 큰 미결 사항이다. 가능한 해석:
   - (a) 번호 입력 즉시 화면에 티켓이 표시되고 이미지로 저장 가능 — 구현 간단, 추가 비용 없음.
   - (b) 문자·카카오톡으로 티켓을 발송 — 발송 솔루션(솔라피 등) 계약과 건당 비용 필요.
   - (c) 당일 입장 확인용 QR — 현장 체크 앱까지 필요.
   - 권장: (a). 필요하면 나중에 (c)를 추가.
3. **[A] 흐름도에서 빠진 단계.** 첨부 흐름도를 그대로 구현하면 아래가 빠진다. 확인 요청:
   - "참석 희망 시간대" 입력 단계가 흐름도에 없다 (요구사항 4-2에는 있음). 참석 여부 → 시간대 → 실물 청첩장 순서로 넣는 것을 제안.
   - "불참" 선택 시의 흐름이 없다. 불참자는 바로 감사 메시지로 종료할지, 불참자도 실물 청첩장을 신청할 수 있게 할지.
   - 이름·동반 인원 필드가 없다. 시간대별 인원 집계를 하려면 최소 이름 + 인원이 필요하다.
   - 마지막 상자 "배송안내 (실물 선택시)"에 모바일 경로도 합류한다. 모바일 선택 시에는 배송 안내가 아니라 티켓 수령 안내가 나와야 하므로, "완료 안내(선택에 따라 분기)"로 해석해 구현한다.
4. **[B] 배송 방법.** 우편인지 택배인지에 따라 우편번호·상세주소·연락처 필수 여부가 달라진다. 우편번호 검색(다음 주소 API, 무료)을 넣을지.
5. **[B] 응답 수정.** 하객이 이미 제출한 응답을 바꾸고 싶을 때 재제출로 덮어쓸지(전화번호 기준), 수정 불가로 두고 연락하라고 안내할지.
6. **[B] 개인정보 안내.** 주소·전화번호를 수집하므로 수집 목적·보관 기간(예: 행사 후 30일 내 삭제)을 한 줄로 명시하는 것을 권장. 문구 확인.

### 2.6 QA / 릴리즈

1. **[B] 두 사람의 실제 휴대폰 기종·OS.** 1차 실기기 테스트 대상.
2. **[C] 카카오톡 미리보기 카드 문구·이미지.** 공유 시 노출되는 제목·설명·썸네일. 콘텐츠 자료와 함께 결정.

## 4. 기술 방향 (제안, 답변에 따라 조정)

- **프론트엔드:** Vite + React + TypeScript, 애니메이션은 `motion`(Framer Motion) 한 종류로 제한. 정적 빌드.
- **스타일:** CSS 변수 기반 토큰 + 모듈 CSS. 레퍼런스 확정 전까지 임시 토큰.
- **데이터:** Google Sheets + Apps Script 웹훅 (기본안). 대안 Supabase.
- **지도:** 정적 이미지 + 네이버지도·카카오맵·티맵 딥링크.
- **배포:** Vercel (또는 GitHub Pages). 커밋마다 프리뷰 URL 생성.
- **성능 예산:** 초기 로딩 LTE 기준 3초 이내, 전체 전송량 1.5MB 이하(이미지 포함), 웹폰트 서브셋 적용.
- **테스트 1순위:** iOS Safari, 카카오톡 인앱 브라우저(iOS/Android), Chrome Android.
